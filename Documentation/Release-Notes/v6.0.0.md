# JC-Packages v6.0.0

**Release date:** 11 August 2026
**Previous version:** 5.1.0

## Overview

v6.0.0 finishes the job v5.0.0 started. v5 moved the tenancy *models* out of JC.Identity into JC.Core; v6 moves the tenancy *engine* out into a package of its own, **JC.Tenancy**, and splits the identity runtime that JC.Identity and a future `JC.CAP` both need into **JC.Identity.Shared** and **JC.Identity.Shared.Web**.

The result is that tenancy no longer arrives with identity. An application can take tenancy without users, identity without tenants, or both — and a worker service can take identity attribution without the ASP.NET Core runtime.

Alongside that, JC.Web gains two whole areas: a **UI framework abstraction** that lets every tag helper in the suite render for Bootstrap 5, Tailwind v4 or jc-tailwind-ui with an independently chosen icon set, and an **SEO** area covering sitemaps, robots.txt, meta tags and JSON-LD. JC.Communication gains **email attachments**.

This is a wide breaking release. Per the [suite versioning policy](../../README.md#versioning-strategy), every package moves to `6.0.0`, including those with no functional changes.

## Highlights

- **New: JC.Tenancy** — the tenancy engine, extracted whole. Tenant scope, EF query filters, a tenant store, caching and cross-tenant access, with no dependency on ASP.NET Core or on any identity package.
- **New: JC.Identity.Shared and JC.Identity.Shared.Web** — the current-user runtime that JC.Identity and a future `JC.CAP` share, split so the framework-free half is usable from a console or worker host.
- **JC.Identity no longer owns tenancy.** `IdentityDataDbContext` has no `Tenants` DbSet, no `CurrentTenantId` and applies no tenant filter. Tenant filtering is now opt-in per DbContext.
- **New: a UI framework abstraction in JC.Web** — no tag helper in the suite hardcodes a CSS class or an icon any more. Bootstrap 5, Tailwind v4 or jc-tailwind-ui, with Bootstrap Icons or Font Awesome 6 chosen separately.
- **New: an SEO area in JC.Web** — sitemap with automatic Razor route discovery, robots.txt, Open Graph and Twitter meta, and typed JSON-LD.
- **New: email attachments in JC.Communication**, with a total-size cap and metadata-only logging.
- **Every package now ships XML documentation**, providing IntelliSense for documented public APIs and enabling compile-time cref validation.
- **Three schema changes**, each conditional on the packages you use — the `SavedFile` tenant foreign key, a new `EmailAttachmentLogs` table, and JC.Tenancy's `Tenants` table. Each needs a migration.

## Breaking changes

### JC.Core

#### `Tenant` and `TenantSettings` moved to JC.Tenancy

| Type | Was | Now |
|------|-----|-----|
| `Tenant` | `JC.Core.Models.MultiTenancy` | `JC.Tenancy.Models` |
| `TenantSettings` | `JC.Core.Models.MultiTenancy` | `JC.Tenancy.Models` |

`IMultiTenancy` **stays in JC.Core**. Marking an entity tenant-scoped remains free and requires no reference to the tenancy engine; only filtering costs a JC.Tenancy reference.

#### `IMultiTenancy` lost its `Tenant` navigation

```csharp
// Before
public interface IMultiTenancy
{
    string? TenantId { get; set; }
    Tenant? Tenant { get; set; }
}

// Now
public interface IMultiTenancy
{
    string? TenantId { get; set; }
}
```

Core cannot require a navigation to a type it no longer owns. More importantly, a tenant-aware entity may live in a context that has never heard of the tenant table — physical foreign keys cannot cross DbContexts or databases — so the mark now means a partition key and nothing more. Any entity declaring `public Tenant? Tenant { get; set; }` to satisfy the interface should delete that property; see the schema section below, because the column it produced is going away.

#### `IUserInfo` gained members and lost one

| Member | Change |
|--------|--------|
| `Authority` | **New.** `IdentityAuthority` — who supplied this identity. |
| `RegistrationUtc` | **New.** `DateTime?`. |
| `HasTenant` | **New.** Get-only, derived from `TenantId`. |
| `MultiTenancyEnabled` | **Removed.** Replaced by `HasTenant`. |

Nothing in the suite ever read `MultiTenancyEnabled`, and being settable it could disagree with the tenant it described — assigning `TenantId` directly left it stale. Replace reads with `HasTenant`, or with `!string.IsNullOrEmpty(userInfo.TenantId)`.

Any custom `IUserInfo` implementation must add the three new members. Deriving from `UserInfoBase` in JC.Identity.Shared gets them for free.

#### `NetworkFamily` enum removed

`JC.Core.Enums.NetworkFamily` (`Net10`, `Net172`, `Net192`) is deleted. Nothing in the suite consumed it.

#### `ToDisplayName` splits digits by default

`string.ToDisplayName()` and `Enum.ToDisplayName()` were rewritten and gained a `splitDigits` parameter defaulting to `true`:

```csharp
"Address1".ToDisplayName();                      // "Address 1"   (was "Address1")
"Address1".ToDisplayName(splitDigits: false);    // "Address1"
```

The rewrite also preserves acronyms (`"XMLParser"` gives `"XML Parser"`) and carries reference codes such as `"BT.23.9"` and `"2024-01-15"` across verbatim. `ToSlug` deliberately passes `splitDigits: false`, so slugs are unchanged — an existing `version2` does not silently become `version-2` and break every link to it.

**Trap:** if you display enum names in a UI and any member name ends in a digit, the rendered text changes. Pass `splitDigits: false` to keep the old output.

### JC.Identity

This is the largest breaking surface in the release. JC.Identity remains the local ASP.NET Core Identity integration; what left it is the tenancy engine and the authority-agnostic parts of the current-user runtime.

#### Types moved to JC.Identity.Shared

| Type | Was | Now |
|------|-----|-----|
| `DefaultClaims` | `JC.Identity.Authentication` | `JC.Identity.Shared.Authentication` |
| `IdentityHelper` | `JC.Identity.Helpers` | `JC.Identity.Shared.Helpers` |
| `IdentityMiddlewareOptions` | `JC.Identity.Models.Options` | `JC.Identity.Shared.Models.Options` |

#### Types moved to JC.Identity.Shared.Web

| Type | Was | Now |
|------|-----|-----|
| `UserInfoMiddleware` | `JC.Identity.Middleware` | `JC.Identity.Shared.Web.Middleware` |
| `IdentityMiddleware` | `JC.Identity.Middleware` | `JC.Identity.Shared.Web.Middleware` |
| `UseUserInfo` / `UseIdentityMiddleware` | `JC.Identity.Extensions` | `JC.Identity.Shared.Web.Extensions` |

The new namespaces are deliberate: a future `JC.CAP` should never have to import a `JC.Identity` namespace to reach types it legitimately shares.

`UseIdentity` stays in `JC.Identity.Extensions` and still composes the pipeline, so an application calling it only needs a `using` change.

#### `AddIdentityBase` removed

Renamed and split, with no `[Obsolete]` forwarders:

| Was | Now | Registers |
|-----|-----|-----------|
| `AddIdentityBase<TUser, TRole>` | `AddIdentityServices<TUser, TRole>` | The JC.Identity half — claims factory, authentication, authorisation |
| `AddIdentityBase<TUser, TRole, TUserInfo>` | `AddIdentityServices<TUser, TRole, TUserInfo>` | As above, with a custom `IUserInfo` |
| — | `AddSharedIdentityServices<TUserInfo>` | The authority-agnostic half — scoped `IUserInfo`, both options types |

The old name predated the Shared package and, once one existed, read as that package's registration call — which it never was. `AddIdentity<TUser, TRole, TContext>` is unchanged and still the recommended entry point.

#### `UserInfo` split

`UserInfoBase` (JC.Identity.Shared) holds the property surface; `UserInfo : UserInfoBase` (JC.Identity) keeps the `BaseUser`-shaped constructors. The derived type keeps the name, so `AddIdentity<AppUser, AppRole, AppDbContext>` and any code naming `UserInfo` is unaffected.

#### `IdentityDataDbContext` no longer does tenancy

Removed: the `Tenants` DbSet, the `Tenant` entity mapping, `CurrentTenantId`, and the `ApplyTenantQueryFilters` call.

`JC.Identity/Extensions/QueryExtensions.cs` is deleted outright, taking `ApplyTenantQueryFilters(ModelBuilder, DbContext)` and `AllTenants<T>(IQueryable<T>, IUserInfo)` with it. Both have replacements in JC.Tenancy with different shapes — see the migration guide.

**This is the most dangerous change in the release.** An application that upgrades, fixes its compile errors and does nothing else will **compile, start, and return every tenant's rows from every tenant-scoped query.** There is no exception, no log line and no failed migration. Read [step 4 of the migration guide](#4-re-establish-tenant-filtering) before deploying.

#### Seeding signatures changed

```csharp
// Before
await app.ConfigureAdminAndRolesAsync<AppUser, AppRole, AppDbContext, AppRoles>(
    setupTenancy: true,
    defaultTenantConfigKey: "Admin:DefaultTenantName");

// Now
var admin = await app.ConfigureAdminAndRolesAsync<AppUser, AppRole, AppRoles>(
    assignAdminRole: true);

if (admin is not null)
    await app.Services.SeedDefaultTenantAsync<AppUser, AppDbContext>(admin.Id);
```

| Change | Detail |
|--------|--------|
| `TContext` type parameter | **Removed** from `ConfigureAdminAndRolesAsync` and `SeedDefaultAdminAsync`. It existed only to reach `context.Tenants`. |
| `setupTenancy` | **Replaced** by `assignAdminRole`, defaulting to `true`. |
| `defaultTenantConfigKey` | **Removed.** The tenant name is now an argument to `SeedDefaultTenantAsync`. |
| Return type | Both now return `TUser?` — the created *or existing* administrator, `null` only where creation was attempted and failed. |

`setupTenancy` had drifted into controlling something it did not name: with tenant seeding commented out it did nothing *except* silently suppress the `Admin` role. The replacement says what it does.

Returning the existing administrator rather than `null` is what makes the follow-on tenant assignment idempotent — a first run that created the user but failed the tenant step corrects itself on the next start.

#### `BaseUser` implements `IApplicationUser`

`IdentityTenantId` is `[NotMapped]` and reads and writes the existing `TenantId` column, so **no migration is required** for this.

`BaseUser` still does **not** implement `IMultiTenancy`, and must not. A global query filter on the user entity breaks `UserManager` and `SignInManager`, because authentication resolves a user before any tenant scope exists.

### JC.FileStorage

#### `SavedFile` lost its `Tenant` navigation and foreign key

Removed from the model, and from `SavedFileMap`:

```csharp
// Removed
builder.HasOne(f => f.Tenant)
    .WithMany()
    .HasForeignKey(f => f.TenantId)
    .OnDelete(DeleteBehavior.SetNull);
```

Two consequences worth stating plainly: the foreign-key constraint disappears from the schema — a real migration, not a no-op — and `OnDelete(SetNull)` goes with it, so deleting a tenant no longer nulls `TenantId` on that tenant's saved files.

The delete behaviour is deliberately **not** replaced. `ITenantStore` soft-deletes, so the cascade would only ever have fired on a direct SQL delete, and nulling the partition key would orphan rows against a later restore.

#### `AddFolders` moved off `IApplicationBuilder`

```csharp
// Before
app.AddFolders(true, "invoices", "reports");

// Now — JC.FileStorage
app.Services.AddFolders(true, "invoices", "reports");

// Or, with JC.FileStorage.Web referenced, the old shape still works
app.AddFolders(true, "invoices", "reports");
```

`JC.FileStorage/Extensions/ApplicationBuilderExtensions.cs` is deleted; the behaviour now lives on `IServiceProvider` in JC.FileStorage, with a convenience `IApplicationBuilder` overload in JC.FileStorage.Web. This is what lets JC.FileStorage run unchanged from a worker service or console host.

#### `StorageService` reads the operational tenant, not the user

`StorageService` resolved `IUserInfo` and used `_userInfo?.TenantId` for every default-path save, read and delete, while `SavedFile` was *filtered* by the tenant scope. Two sources of truth for the same question: they agreed in an ordinary authenticated request and diverged everywhere else — a background job scoped to a tenant wrote files it could not then see.

It now resolves `ITenantContext` from JC.Core, optionally, so no tenancy registered still means the null partition.

**Trap:** if your application previously relied on files being written under the *user's* tenant while reading them under a different scope, that inconsistency is gone. Files now go where the scope says.

### JC.Web

#### UI helpers are no longer static

| Type | Was | Now |
|------|-----|-----|
| `AlertHelper` | `static class` | Instance, injected, takes `IWebFrameworkDictionary` |
| `HtmlHelper` | `static class` | Instance, injected, takes `IWebFrameworkDictionary` |
| `BreadcrumbBuilder` | `new BreadcrumbBuilder()` | `new BreadcrumbBuilder(dictionary)` |
| `TableBuilder<T>` | `new TableBuilder<T>()` | `new TableBuilder<T>(dictionary)` |

They cannot be static any more because the CSS class names now come from a swappable dictionary rather than being hardcoded to Bootstrap. `AlertHelper` and `HtmlHelper` are registered as singletons by `AddUI`; the two builders are constructed per use and take the dictionary directly.

```csharp
// Before
var html = AlertHelper.Success("Saved.");

// Now
public class MyPage(AlertHelper alerts)
{
    public string Render() => alerts.Success("Saved.");
}
```

#### `HtmlTagBuilder` lost two methods

`AddActiveAttribute()` and `AddDisabledClass()` are removed. Active and disabled states are now resolved through the framework dictionary, since the class names differ per framework.

#### `BugReporterTagHelper.Colour` is now nullable

`string` defaulting to `"danger"` becomes `string?` defaulting to `null`. A null value takes the configured framework's own default rather than assuming a Bootstrap class name.

#### Tag helpers now have constructor dependencies

Every tag helper in JC.Web, JC.Communication.Web and JC.FileStorage.Web now injects a framework dictionary, `HtmlHelper`, or both.

**Trap, and the most likely one to bite:** if the registration call is missing, nothing fails at build or at start-up. The failure happens **when a page renders**. Call `AddUI()`, or one of the `AddWebDefaults` / `AddCommunicationWeb` / `AddFileStorageWeb` methods that call it for you.

#### Cookie data-protection configuration key moved

```json
// Before
{ "Cookies": { "DataProtection_Path": "/path/to/keys" } }

// Now
{ "Web": { "Cookies": { "DataProtection_Path": "/path/to/keys" } } }
```

**Trap:** encrypted cookies throw at start-up when the key is absent, so this one fails loudly — but it fails in an application that was working a moment ago, and the message names the new key, not the old one.

#### Rate limiting defaults to a sliding window

`RateLimitingOptions.Strategy` now defaults to `RateLimitingStrategy.SlidingWindow` rather than `FixedWindow`. Set it explicitly to keep the old behaviour.

#### Rate limiting honours `TrustProxyHeaders`

The rate-limit partition key previously resolved the client IP without consulting `ClientIpOptions`, so it always used the socket address. It now passes `ClientIpOptions.TrustProxyHeaders` through.

This changes nothing unless you had already opted into `TrustProxyHeaders = true`, in which case rate limiting now partitions by the proxy-supplied address — which is what you asked for, and almost certainly what you wanted.

### JC.Communication

#### `NotificationUIHelper` removed

`JC.Communication.Notifications.Helpers.NotificationUIHelper.GetIconClass(NotificationType)` is deleted. It returned hardcoded Bootstrap Icons class names, which is a presentation decision that JC.Communication — a package referencing only JC.Core — has no business making.

Default icons and colours per `NotificationType` now live on the icon and class dictionaries in JC.Communication.Web, selected by the configured framework. Override per notification with `NotificationStyle`.

#### `IEmailDbContext` gained a DbSet

```csharp
DbSet<EmailAttachmentLog> EmailAttachmentLogs { get; set; }
```

Any application implementing `IEmailDbContext` itself must add it. Applications using the supplied contexts get it automatically, but still need a migration — see the schema section.

#### `ValidateEmailMessage` gained a parameter

```csharp
// Before
public string? ValidateEmailMessage()

// Now
public string? ValidateEmailMessage(long maxTotalAttachmentBytes = 0)
```

The parameter is optional, so existing calls compile unchanged.

## New features

### JC.Tenancy

The tenancy engine, extracted from JC.Identity. Depends on JC.Core only — **no ASP.NET Core dependency and no identity dependency**, so it behaves identically in a request, a background job and a console application. See [Setup](../JC.Tenancy/Setup.md) and [Guide](../JC.Tenancy/Guide.md).

**Tenant scope.** `ITenantInfo` is registered scoped and derives the tenant live from `IUserInfo` unless set explicitly. Establish it deliberately with:

```csharp
services.SetTenantInfoForTenant(tenantId);          // by identifier
services.SetTenantInfoForTenant(tenant);            // from an already-loaded record
await services.SetTenantInfoForDomainAsync(domain); // resolve by domain
using var scope = services.CreateScopeForTenant(tenantId);
await using var scope = await services.CreateAsyncScopeForTenantByDomain(domain);
```

Assigning `TenantId` — including assigning `null` — sets an override that wins for the rest of the scope. `IsOverridden` reports whether the tenant was set explicitly or derived from the user.

**EF query filters.** `ApplyTenantFilters` installs a global query filter over every `IMultiTenancy` entity in a model, matching null to null so the null partition behaves as a partition rather than as "no filtering". It binds to `ITenantScopedContext.CurrentTenantId` on the DbContext rather than to `ITenantInfo` — an EF Core constraint, not a preference. EF caches the compiled model per context type but re-reads a captured `DbContext`'s members against the active instance on every query; no equivalent allowance exists for an arbitrary service, so a filter closing over the scoped `ITenantInfo` would bake whichever tenant warmed the model into every later request.

**Tenant storage.** `AddTenancy<TContext>` is constrained to `ITenantDbContext` and throws on a second registration, so exactly one context owns the tenant table. Many contexts may be *filtered* — that only requires `ITenantScopedContext`.

**The store.** `ITenantStore` is the supported read/write boundary: `GetAsync`, `GetByNameAsync`, `GetByDomainAsync`, `GetAllAsync` (list and paged overloads), `TryAddAsync`, `TryUpdateAsync`, `TryDeleteAsync` (soft), `TryRestoreAsync` and `TrySetSettingAsync`. Mutations enforce unique names and domains and invalidate the cache. Direct EF writes bypass invalidation and stay stale until the entry expires — documented and accepted.

**Caching.** `IMemoryCache`, five-minute default lifetime, configurable through `TenantOptions.CacheEnabled` and `CacheLifetime`. Misses are cached too, so an unknown identifier does not hit the database on every read.

**Cross-tenant access.** `query.AllTenants(authoriser)` is gated by `ITenantBypassAuthoriser`; the default implementation matches the current user against role *names* in `TenantOptions.BypassRoles`. Names rather than a constant, because JC.Tenancy and the identity packages are siblings and neither may reference the other. It denies when no roles are configured and denies when no user resolves, so an application that has not considered cross-tenant access has not accidentally granted it — and warns once when it refuses for want of configuration, so the silence is not mistaken for a role check failing.

`query.AllTenantsUnsafe()` bypasses the check entirely, for trusted work with no user to authorise.

**Seeding.** `TenantSeeder` and `SeedDefaultTenantAsync` create an application's default tenant and optionally assign it to a user, both idempotent.

### JC.Identity.Shared and JC.Identity.Shared.Web

The current-user runtime that JC.Identity and a future `JC.CAP` share, extracted so neither has to reimplement it.

`JC.Identity.Shared` carries **no ASP.NET Core dependency**. It holds `UserInfoBase`, the claims projection, `IdentityRules` (the disabled-account, password-change and two-factor rules, expressed as a function returning a route or nothing), `DefaultClaims`, `IdentityHelper` and both options types. It defines no roles — an authority's administrative roles are its own security domain, so `SystemRoles` stays in JC.Identity. `UserInfoExtensions` establishes an ambient identity outside a request:

```csharp
await using var scope = services.CreateAsyncScopeForUser(user, roles, user.IdentityTenantId);
```

`JC.Identity.Shared.Web` holds the two middlewares and their builder extensions. Both are thin wrappers over the framework-free half, so an authority with no HTTP pipeline reaches identical behaviour without needing the ASP.NET Core shared runtime.

`IdentityProjectionOptions` names the identifier, email and role claim types plus the authority to stamp, so the projection does not need to know who authenticated the user. JC.Identity populates it through an `IConfigureOptions<>` rather than eagerly, so an application that reconfigures `IdentityOptions.ClaimsIdentity` after `AddIdentity` is still honoured.

### JC.Core

- **`IApplicationUser`** — the authoritative user-record contract, describing *any* user rather than only the one signed in. Read/write, because storage is not a one-way concern. `BaseUser` implements it.
- **`IdentityAuthority`** — `None`, `Local`, `CAP`, `Custom`, exposed as `IUserInfo.Authority`. It names who supplied the identity, not how they established it. Defaults to `None`, so an authority that never declares itself cannot silently pass as local.
- **`ITenantContext`** — a read-only view of the operational tenant, in Core so a package can read the current tenant for entities it has marked `IMultiTenancy` without referencing JC.Tenancy. Resolve it optionally; no tenancy registered means the null partition.
- **`IUserInfo.SystemUser<T>()` and `UnknownUser<T>()`** — static factories for the system and unknown identities.

### JC.Web — UI framework abstraction

`UIFramework` (`Bootstrap`, `Tailwind`, `CustomJCTailwind`) and `IconFramework` (`Bootstrap`, `FontAwesome`) are chosen independently:

```csharp
builder.Services.AddUI(UIFramework.Tailwind, IconFramework.FontAwesome);
```

Both are `[Flags]`, and `UIFrameworkService` resolves a combination down to a single value once at registration — `CustomJCTailwind` beats `Tailwind` beats `Bootstrap`; `Bootstrap` beats `FontAwesome` — so nothing downstream ever handles unresolved flags.

`AddFrameworkDictionary<T>` and `AddIconDictionary<T>` let a package register its own dictionary against the same resolved choice, which is how JC.Communication.Web and JC.FileStorage.Web stay in step with the application's selection.

Tailwind safelists ship as content files (`jc-web.tailwind.css`, `jc-communication.tailwind.css`, `jc-filestorage.tailwind.css`) because Tailwind's scanner cannot see class names inside a compiled assembly. Import the relevant one from your entry CSS.

### JC.Web — SEO

An entirely new area:

- **Sitemap** — `AddSitemap` / `UseSitemap`, discovering Razor routes automatically, splitting behind an index past the protocol limit. `ISitemapUrlProvider` adds dynamic URLs; `[SitemapIgnore]` excludes a page.
- **robots.txt** — `AddRobots` / `UseRobots`, with a `Sitemap:` directive emitted only when a sitemap is actually being served.
- **Meta tags** — a `<seo-meta>` tag helper for Open Graph and Twitter cards.
- **JSON-LD** — `SeoBuilder` with typed schema objects.

`UseSeo()` composes the sitemap and robots middleware. Both `AddSitemap` and `AddRobots` take an optional `IConfiguration` for `appsettings.json` binding, or a configure callback.

### JC.Communication — email attachments

```csharp
var message = new EmailMessage(...)
    .WithAttachment("invoice.pdf", pdfBytes)
    .WithAttachment(new EmailAttachment("terms.pdf", termsBytes, "application/pdf"));
```

`EmailOptions.MaxTotalAttachmentBytes` caps the combined size, defaulting to 18 MB. `ValidateEmailMessage(maxTotalAttachmentBytes)` enforces it and validates each attachment.

Attachments are logged as **metadata only** — file name, MIME type and size, in a new `EmailAttachmentLogs` table. Content is never persisted.

### Suite-wide

- **XML documentation now ships in every package**, so consumers get IntelliSense from the `///` comments. This also turns on cref validation in the build.
- **Every package gained a `README.md`**, packed as the landing page on a feed and the front page on GitHub.
- **Repository moved** to `github.com/JC-Foundry/JC-Packages`, with `Company`, `Product` and `Copyright` metadata added.

## Migration guide

Work through these in order. Steps 1–3 are compile errors that will find you; **step 4 is the one that does not**, and step 5 covers the schema.

### 1. Update package references

Add the new packages you need:

| If you… | Add |
|---------|-----|
| Use multi-tenancy at all | `JC.Tenancy` |
| Use JC.Identity | Nothing — `JC.Identity.Shared` and `JC.Identity.Shared.Web` come with it |
| Want identity attribution in a non-web host | `JC.Identity.Shared` alone |
| Register storage folders in a web app | `JC.FileStorage.Web`, or switch to `app.Services.AddFolders(...)` |

### 2. Update namespaces

```csharp
// Tenancy models
- using JC.Core.Models.MultiTenancy;   // for Tenant / TenantSettings
+ using JC.Tenancy.Models;
// (keep JC.Core.Models.MultiTenancy where you use IMultiTenancy or ITenantContext)

// Identity types that moved to Shared
- using JC.Identity.Authentication;    // DefaultClaims only — SystemRoles stays put
+ using JC.Identity.Shared.Authentication;

- using JC.Identity.Helpers;           // IdentityHelper
+ using JC.Identity.Shared.Helpers;

- using JC.Identity.Models.Options;    // IdentityMiddlewareOptions
+ using JC.Identity.Shared.Models.Options;

// Middleware and its builder extensions
- using JC.Identity.Middleware;
+ using JC.Identity.Shared.Web.Middleware;
```

If you call `UseIdentity()` and nothing else from the middleware namespaces, you need no `using` change at all — it still lives in `JC.Identity.Extensions`.

### 3. Update renamed and reshaped calls

```csharp
// Registration
- builder.Services.AddIdentityBase<AppUser, AppRole>();
+ builder.Services.AddIdentityServices<AppUser, AppRole>();

// Seeding — TContext dropped, returns the administrator
- await app.ConfigureAdminAndRolesAsync<AppUser, AppRole, AppDbContext, AppRoles>(setupTenancy: true);
+ var admin = await app.ConfigureAdminAndRolesAsync<AppUser, AppRole, AppRoles>();
+ if (admin is not null)
+     await app.Services.SeedDefaultTenantAsync<AppUser, AppDbContext>(admin.Id);

// Cross-tenant queries
- var all = query.AllTenants(_userInfo);
+ var all = query.AllTenants(_bypassAuthoriser);   // inject ITenantBypassAuthoriser

// Folder registration
- app.AddFolders(true, "invoices");
+ app.Services.AddFolders(true, "invoices");       // or keep app.AddFolders with JC.FileStorage.Web

// IUserInfo
- if (userInfo.MultiTenancyEnabled)
+ if (userInfo.HasTenant)

// JC.Web UI helpers — inject rather than call statically
- var markup = AlertHelper.Success("Saved.");
+ // constructor: MyService(AlertHelper alerts)
+ var markup = alerts.Success("Saved.");
```

Remove any `public Tenant? Tenant { get; set; }` property you added purely to satisfy `IMultiTenancy`.

### 4. Re-establish tenant filtering

**Do not skip this.** In v5, `IdentityDataDbContext.OnModelCreating` applied tenant filters itself, so every application inheriting from it was filtered whether or not it knew. In v6 that call is gone and filtering is opt-in per context. An application that upgrades and does nothing here compiles, starts and silently returns every tenant's rows.

Register the engine against the context that owns tenant storage:

```csharp
builder.Services.AddTenancy<AppDbContext>(options =>
{
    options.AllowBypassForRole(SystemRoles.SystemAdmin);   // otherwise nobody may cross tenants
});
```

Then make each tenant-scoped context declare and apply it:

```csharp
public class AppDbContext(DbContextOptions options, IUserInfo userInfo, ITenantInfo tenantInfo)
    : IdentityDataDbContext<AppUser, AppRole>(options, userInfo), ITenantScopedContext, ITenantDbContext
{
    public string? CurrentTenantId => tenantInfo.TenantId;

    public DbSet<Tenant> Tenants { get; set; }

    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        base.OnModelCreating(modelBuilder);

        modelBuilder.ApplyTenancyMappings();   // only in the context that owns tenant storage
        modelBuilder.ApplyTenantFilters(this); // last — see the trap below
    }
}
```

`ITenantDbContext` and `ApplyTenancyMappings()` belong to the **one** context that owns the tenant table. Every other tenant-filtered context implements `ITenantScopedContext` and calls `ApplyTenantFilters(this)` only.

**Trap — `ApplyTenantFilters` must be called last.** It reads the model at the moment it is called, so any `IMultiTenancy` entity you register *after* it never gets a filter. Worse, if you call it before registering any tenant-scoped entity at all, it finds nothing, returns quietly, and the guard that would otherwise have thrown never runs.

**Trap — the guard only fires when it can see tenant entities.** `ApplyTenantFilters` throws when a model holds `IMultiTenancy` entities but the context does not implement `ITenantScopedContext`. That is a genuine safety net, but only if you call the method. *Not* calling it is the silent path, and it is the default after upgrade.

Verify by scoping to a tenant that owns data and confirming a query returns only its rows.

[JC.Tenancy — Setup](../JC.Tenancy/Setup.md) covers the registration options in full, including entity exclusions and cache configuration.

### 5. Generate migrations

Three schema changes, each conditional on which packages you use, in one migration:

```bash
dotnet ef migrations add V6Upgrade --project YourApp
dotnet ef database update --project YourApp
```

**Review the generated migration before applying it.** Expect these, and nothing else:

| Change | Applies if you use | Notes |
|--------|--------------------|-------|
| `SavedFiles` foreign key dropped | JC.FileStorage | `SavedFile.Tenant` navigation removed. The `TenantId` column stays; only the constraint goes. |
| `EmailAttachmentLogs` table added | JC.Communication's email logging | Indexed on `EmailLogId`. |
| `Tenants` table and its unique index on `Name` | JC.Tenancy | New table in whichever context you nominate through `AddTenancy<TContext>`. See the trap below. |

**`AuditEntries` does not change.** Its column lengths are set by `AuditEntryMapping`, which is unchanged from v5, and fluent configuration wins over the model's attributes — so the columns are, and always were, `Id` 36, `EntityKey` 512, and `UserId`, `UserName`, `ActionUserId`, `SourceApplication` and `TableName` 256 each. If your generated migration proposes altering these columns, something else in your model is the cause.

**Trap — the unique index on `Tenants.Name` fails where duplicates already exist.** Deduplicate first. Note also that soft-deleted tenants keep their name permanently, so a deleted name is never freed — which is deliberate, since it means a restore can never clash.

`Domain` is indexed but **not** uniquely: it is nullable, and SQL Server would then permit only one tenant without a domain while MySQL would permit many. A provider-agnostic mapping cannot express "unique except nulls".

**Trap — the tenant table name for JC.Core-only applications.** Under v5, an application whose context reached `Tenant` only through `SavedFile`'s navigation got a table named `Tenant`, from the type name. In v6 the entity enters the model through `ITenantDbContext.Tenants`, so the table is `Tenants`. If you are in that position, expect a rename in the migration and check it is a rename rather than a drop-and-create.

**If you are not adopting JC.Tenancy at all**, `Tenant` no longer enters your model through JC.FileStorage, so the table becomes orphaned. Dropping it is your call; nothing in the suite reads it.

### 7. Choose a UI framework, if you use tag helpers

If you were using JC.Web, JC.Communication.Web or JC.FileStorage.Web tag helpers, register the UI services:

```csharp
builder.Services.AddWebDefaults(builder.Configuration);          // Bootstrap defaults
builder.Services.AddCommunicationWeb();                          // if using JC.Communication.Web
builder.Services.AddFileStorageWeb();                            // if using JC.FileStorage.Web
```

All three default to Bootstrap 5 and Bootstrap Icons, which is what v5 rendered, so passing nothing keeps the old appearance. To change:

```csharp
builder.Services.AddWebDefaults(builder.Configuration,
    uiFramework: UIFramework.Tailwind,
    iconFramework: IconFramework.FontAwesome);
```

The per-package calls use `TryAdd`, so whichever runs first wins and every dictionary resolves against the same choice. On Tailwind, import the safelist CSS each package ships.

**Trap:** omitting the registration fails at **render time**, not at start-up. A page that never renders a tag helper will look fine.

### 8. Review two behaviour changes

- **`ToDisplayName`** now splits digits from letters. Pass `splitDigits: false` where you need the old output. Slugs are unaffected.
- **Rate limiting** now defaults to a sliding window. Set `Strategy = RateLimitingStrategy.FixedWindow` to keep the old behaviour.

## Notes and limitations

- **Filtering is opt-in, and forgetting it is silent.** This is the single most important thing in the release. `ApplyTenantFilters` throws when a model holds tenant-scoped entities and the context cannot say which tenant is current — but only if you call it. Not calling it is the default after upgrade, and it exposes every tenant's rows without an exception, a log line or a failed migration.
- **`BaseUser` is tenant-aware but not tenant-filtered.** It carries and persists a tenant, and that tenant flows into claims and `IUserInfo`. It is deliberately not subject to automatic filtering: a global query filter on the user entity breaks `UserManager` and `SignInManager`, which resolve a user before any tenant scope exists. The same caution applies to any entity ASP.NET Identity queries during authentication.
- **A null tenant is a partition, not a wildcard.** Filters match null to null, so rows with `TenantId = NULL` are visible only in the null partition — unchanged from v5.
- **JC.Tenancy does not enforce tenant policy.** `MaxUsers`, `ExpiryDateUtc` and `Domain` are reported through `ITenantInfo`; `IsExpired` tells you the expiry has passed. Nothing acts on any of them. Whether an expired tenant may still be used is application policy.
- **Deleting a tenant does not cascade.** `TryDeleteAsync` soft-deletes the tenant record only. Rows elsewhere keep their `TenantId`, because tenant-scoped data can live in contexts and databases the store has never heard of. Query filters compare strings and never touch the tenant table, so data access is unaffected; only metadata reads go null, and a restore brings everything back intact.
- **Direct EF writes to `Tenant` bypass cache invalidation.** Changes made outside `ITenantStore` stay invisible until the entry expires — five minutes by default. This is accepted rather than defended against.
- **Tenant cache concurrency is unaddressed.** Two scopes missing simultaneously will both load, and there is no distributed invalidation across instances. Harmless for a single instance; worth knowing before running several.
- **JC.Tenancy configures no foreign keys.** `IMultiTenancy` marks a partition, not a relationship, and it has to mean the same thing whether or not `Tenant` shares the model. An application whose model holds both can configure one itself.
- **Cross-tenant access is denied until configured.** `TenantOptions.BypassRoles` is empty by default, so `AllTenants` refuses everyone — including `SystemAdmin` — until a role is named. This is deliberate: an application that has not thought about cross-tenant access has not accidentally granted it. The refusal is warned about once, so it is not mistaken for a role check simply failing.
- **`AllTenantsUnsafe` drops every global filter on the entity**, not only the tenant one, because `IgnoreQueryFilters` is all-or-nothing. Soft-delete is unaffected — it is applied by `FilterDeleted`, not as a global filter.
- **The Tailwind safelists are not optional on Tailwind.** Tailwind's scanner cannot see class names compiled into an assembly, so without importing the safelist the classes are stripped from your build and the components render unstyled.
- **`JC.Identity.Shared` is framework-free; `JC.Identity.Shared.Web` is not.** A worker service can take the first alone and get identity attribution without requiring the ASP.NET Core shared runtime. Taking JC.Identity pulls in both.
