# JC-Packages v7.0.0

**Release date:** 25 August 2026
**Previous version:** 6.1.0

## Overview

A narrow breaking release with one idea in it: the identity account rules stop being a property of the application and become a property of a **rule set**.

Until now, `IdentityMiddlewareOptions` carried one set of routes and one pair of enforcement switches, applied to every authenticated request. That is correct for an application serving one audience and wrong for one serving two. An application that hosts its own pages alongside a single sign-on surface needs the same behaviours in both places, at different routes: a disabled user must still be stopped, a forced password reset must still fire, and two-factor may be required on one and not the other. A path-exclusion list cannot express that, because it disables every rule for those paths rather than substituting different ones.

`IdentityMiddlewareOptions` now holds an ordered list of `IdentityRuleSet`, each carrying its own routes, its own switches and a condition. The first whose condition matches a request decides everything about it, including which paths are excluded. A `Default` set catches whatever matches nothing, and cannot be removed.

The rest of the release is removal. Every member marked `[Obsolete]` before this release is gone, which takes `ContentSanitiser` out of JC.Web for good and drops that package's dependency on `HtmlSanitizer`.

There are no schema changes and no migrations. Per the [suite versioning policy](../../README.md#versioning-strategy), every package moves to `7.0.0`, including those with no functional change.

## Highlights

- **Account rules are now rule sets.** `IdentityMiddlewareOptions.Default` plus an ordered `RuleSets` list, each entry with a `Condition`, matched first-wins.
- **Conditions can read the request's services**, so a rule set can depend on something that was not knowable at registration, such as a policy an application's own administrators control.
- **`IdentityRules` chooses the set**, not the middleware, so a worker service, a Blazor circuit or a minimal API filter gets rule sets on the same terms as the ASP.NET Core pipeline.
- **`ContentSanitiser` has left JC.Web.** It lives in JC.Content, where it moved in 6.1.0. JC.Web no longer references `HtmlSanitizer`.
- **Every previously obsolete member is removed.** Nine public members across JC.Core, JC.FileStorage and JC.Web.

## Breaking changes

### JC.Identity.Shared

**`IdentityMiddlewareOptions` no longer carries the routes and switches.** They now live on `IdentityRuleSet`, in `JC.Identity.Shared.Models`. The options type holds the sets:

| Member | Type | Description |
|--------|------|-------------|
| `Default` | `IdentityRuleSet` | Applied when no entry in `RuleSets` matches |
| `RuleSets` | `List<IdentityRuleSet>` | The conditional sets, tried in the order they were added |
| `AddForPathPrefix(string, Action<IdentityRuleSet>)` | `IdentityMiddlewareOptions` | Adds a set matching a path prefix, compared case-insensitively |

Everything an application previously set on the options object it now sets on `Default`. Nothing else about those seven properties changed: same names, same types, same defaults.

**`ExcludedPaths` is now evaluated against the selected set.** It was always derived from `AccessDeniedRoute`, `LogoutRoute` and `ErrorRoute`; those routes now belong to whichever set matched. An application with one rule set sees no difference. An application with more than one must keep each set's condition and its routes in agreement, or a set's own logout page will be judged by a different set.

**Selection happens inside `IdentityRules.GetRedirect`.** The existing call still compiles, because `options` is still an `IdentityMiddlewareOptions`, but it now chooses a rule set before evaluating anything. Two additions:

- The options overload takes an optional trailing `IServiceProvider? services`, placed on the context handed to each condition.
- A second overload takes an `IdentityRuleSet` in place of `options` and `services`, for a caller that has already chosen one.
- `SelectRuleSet(IdentityRuleContext, IdentityMiddlewareOptions)` is public, returning the set the rules would apply.

**New types.** `IdentityRuleSet` and `IdentityRuleContext`, both in `JC.Identity.Shared.Models`.

### JC.Core

`RegisterRepositoryContext<T>` and `RegisterRepositoryContexts(params Type[])` are removed from `ServiceCollectionExtensions`. Both were `[Obsolete(error: true)]`, so no code that compiles against 6.x can be calling them. Use `IRepositoryManager`.

### JC.FileStorage

Five public members removed, each of which forwarded to its replacement:

| Removed | Replacement |
|---------|-------------|
| `FolderModel.MaxAllowedBytes` | `ValidationHelper.MaxAllowedBytes` |
| `FolderModel.BlockedExtensions` | `ValidationHelper.BlockedExtensions` |
| `FolderModel.IsBlockedExtension(string)` | `ValidationHelper.IsBlockedExtension(string)` |
| `FolderModel.NormaliseExtension(string, bool)` | `NormalisationHelper.NormaliseExtension(string, bool)` |
| `SavedFile.NormaliseFileName(string)` | `NormalisationHelper.NormaliseFileName(string)` |

Two internal helpers on `FolderModel`, `ValidateAllowedExtensions` and `ValidateMaxBytes`, went with them.

`FolderModel.MaxAllowedBytes` was a `const`, so its value is inlined into anything already compiled against it. A recompile is required, which a major release implies in any case.

### JC.Web

`ContentSanitiser` and `ContentSanitiserOptions` are removed from `JC.Web.UI.Helpers`. They moved to JC.Content in 6.1.0 and have been obsolete since:

| Removed | Replacement |
|---------|-------------|
| `JC.Web.UI.Helpers.ContentSanitiser` | `JC.Content.Helpers.ContentSanitiser` |
| `JC.Web.UI.Helpers.ContentSanitiserOptions` | `JC.Content.Models.Options.ContentSanitiserOptions` |

The implementation is unchanged, so the only edit is the `using`.

**JC.Web no longer references `HtmlSanitizer`.** Those two types were its only use of `Ganss.Xss`. An application that was relying on JC.Web to bring the package in transitively must reference JC.Content, or `HtmlSanitizer` directly.

## New features

### Rule sets

A single-audience application configures `Default` and is finished:

```csharp
builder.Services.AddIdentity<AppUser, AppRole, AppDbContext>(configureMiddleware: options =>
{
    options.Default.EnforceTwoFactor = true;
});
```

An application serving a second audience adds a set for it. `AddForPathPrefix` covers the common case:

```csharp
builder.Services.AddIdentity<AppUser, AppRole, AppDbContext>(configureMiddleware: options =>
{
    options.Default.EnforceTwoFactor = true;

    options.AddForPathPrefix("/sso", ruleSet =>
    {
        ruleSet.EnforceTwoFactor = false;
        ruleSet.TwoFactorRoute = "/sso/security/authenticator";
        ruleSet.ChangePasswordRoute = "/sso/account/set-password";
        ruleSet.AccessDeniedRoute = "/sso/denied";
        ruleSet.LogoutRoute = "/sso/sign-out";
        ruleSet.ErrorRoute = "/sso/error";
    });
});
```

A user without two-factor reaching `/reports` is sent to the application's own enrolment page; the same user reaching `/sso/authorise` is not, because the set that matched does not enforce it. Both are still stopped when the account is disabled, each at their own access-denied page.

Where the discriminator is not a path, add a set directly. The condition is any `Func<IdentityRuleContext, bool>`, and the context carries the path, the authentication state, the projected `IUserInfo` and the request's `IServiceProvider`:

```csharp
options.RuleSets.Add(new IdentityRuleSet
{
    Name = "external",
    Condition = context => context.User.Authority == IdentityAuthority.CAP,
    AccessDeniedRoute = "/external/denied"
});
```

`Name` appears in every redirect log entry, which is what tells you which set fired when two overlap.

### Selection is part of the rules, not the middleware

`IdentityRules.GetRedirect` selects the set itself, after the unauthenticated and static-file checks and before anything else. Two consequences worth stating:

- A host with no ASP.NET Core pipeline gets rule sets by calling the same method it already called.
- A condition never runs on a stylesheet, so the cost of a condition is bounded to real requests.

## Migration guide

### 1. Update package references

Move every JC package to `7.0.0`.

```xml
<PackageReference Include="JC.Identity" Version="7.0.0" />
```

### 2. Reshape the identity middleware callback

The one edit every application using JC.Identity or JC.Identity.Shared has to make:

```csharp
// v6
builder.Services.AddIdentity<AppUser, AppRole, AppDbContext>(configureMiddleware: options =>
{
    options.RequirePasswordChange = true;
    options.EnforceTwoFactor = true;
    options.AccessDeniedRoute = "/account/denied";
});

// v7
builder.Services.AddIdentity<AppUser, AppRole, AppDbContext>(configureMiddleware: options =>
{
    options.Default.RequirePasswordChange = true;
    options.Default.EnforceTwoFactor = true;
    options.Default.AccessDeniedRoute = "/account/denied";
});
```

Registration and pipeline signatures are unchanged. `AddIdentity`, `AddIdentityServices`, `AddSharedIdentityServices`, `UseIdentity`, `UseUserInfo` and `UseIdentityMiddleware` all take exactly what they took in 6.x.

### 3. Repoint ContentSanitiser

```csharp
// v6
using JC.Web.UI.Helpers;

// v7
using JC.Content.Helpers;          // ContentSanitiser
using JC.Content.Models.Options;   // ContentSanitiserOptions
```

Add a JC.Content package reference if the application does not already have one. The types and their behaviour are unchanged.

### 4. Replace the removed JC.FileStorage statics

Only if you called them. Each maps one-for-one onto `ValidationHelper` or `NormalisationHelper`, listed in the table above.

### 5. Rebuild

There are no schema changes and no migrations to generate. A clean build is the whole of the verification.

## Notes and limitations

- **The first matching set wins, and a set with no condition matches everything.** Anything added after such a set is unreachable. Order the list from most specific to least.
- **`Default` is not in the list, and cannot be put there.** That is what stops a mis-ordered or exhaustive-looking set of conditions from leaving a request unenforced: a request matching nothing still meets a set that stops a disabled account.
- **A set's excluded paths are its own.** `ExcludedPaths` is built from the selected set's access-denied, logout and error routes. A set whose condition does not cover its own logout page will have that page judged by whichever set does match.
- **Conditions must not throw.** An exception propagates out of the middleware rather than being treated as a non-match. They also run on every authenticated non-static request, so anything reaching a database wants caching.
- **Two-factor enforcement is still enrolment, not session state.** `IUserInfo.TwoFactorEnabled` is the per-user enrolment flag. Under stock ASP.NET Core Identity an enrolled user is challenged at every sign-in, so enrolled implies verified; the exception is Identity's `TwoFactorRememberMe` cookie, which lets an enrolled user sign in without the challenge on a remembered browser. An application offering "remember this browser" should know that the rules cannot see the difference.
- **No schema changes.** Nothing in this release touches an entity, a column or a migration.
