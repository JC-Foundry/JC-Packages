# JC-Packages v7.1.0

**Release date:** 4 September 2026
**Previous version:** 7.0.1

## Overview

A minor release, additive throughout. It brings one new package, **JC.CAP**, the second identity authority built on JC.Identity.Shared: an application signs its users in at CAP, the Central Admin Portal, and gets back an ordinary cookie session with `IUserInfo` populated, so the rest of the suite works exactly as it does under JC.Identity.

The shared identity runtime gains two things JC.CAP needed and JC.Identity benefits from as well: the account rules now carry a return URL on every redirect, and the reflection that reads a roles class lives in one place, returning a `RoleRecord`. That last change alters the return type of JC.Identity's `SystemRoles.GetAllRoles`, and is the only part of this release that can ask anything of an existing application.

Nothing is removed and no schema changes. Per the [suite versioning policy](../../../README.md#versioning-strategy), every package moves to `7.1.0`, including those with no functional change.

## Highlights

- **New: JC.CAP.** Single sign-on against CAP through an OpenIddict client, with a token-backed session that refreshes silently, CAP's claims translated into ASP.NET Identity's vocabulary, role publishing to CAP, a client for CAP's API, a member cache, and branded links into CAP's account pages.
- **Account-rule redirects carry a return URL.** `IdentityRules.GetRedirect` appends the request's URL to a local route as the rule set's new `ReturnUrlParameter`, and `IdentityMiddleware` passes it, so a page the rules send a user to can bring them back.
- **`RoleRecord` replaces the role tuple.** `SystemRoles.GetAllRoles<T>()` in JC.Identity, and its new counterpart in JC.CAP, return `List<RoleRecord>` from one shared implementation in JC.Identity.Shared.
- **`LocalUrlHelper` in JC.Core**, the local-URL test that keeps a return URL from becoming an open redirect, for code with no `IUrlHelper` to ask.
- Redundant package references dropped from five projects, where JC.Core already supplies the package.

## New: JC.CAP

JC.CAP is to CAP what JC.Identity is to ASP.NET Core Identity: it owns the authentication scheme, the cookie, the `IUserInfo` and the account-rule defaults for its audience. What it does not own is anything CAP owns: credentials, the second factor, registration, account management and the decision of who may sign in. There is no user table and no `DbContext`.

```csharp
builder.Services.AddCore<AppDbContext>();
builder.Services.AddCap(builder.Configuration);

var app = builder.Build();
app.UseCap();
app.MapCap();
await app.SyncCapRolesAsync<AppRoles>();
```

```json
{
  "SSO": {
    "BaseUrl": "https://sso.example.com",
    "ClientId": "evbfqxmh",
    "ClientSecret": "the-secret-CAP-showed-once"
  }
}
```

The configuration section is the one CAP itself reads, taken from the `CAP.SSO` contract package, so the SSO host is named once on both sides. Startup fails if the host, the client id or the secret is missing.

| Area | What it does |
|------|--------------|
| Sign-in | The cookie is the default scheme. An `[Authorize]` challenge lands on a local trigger that sends the browser to CAP's authorize endpoint; CAP returns a code to a mapped callback, which is exchanged for tokens and becomes the session. A browser already signed in at CAP is never prompted again |
| Claims | `CapClaimsPrincipalFactory` translates CAP's OIDC claims onto the cookie in ASP.NET Identity's vocabulary, so `[Authorize(Roles = ...)]`, `User.IsInRole` and `IUserInfo.IsInRole` work with no configuration. `ICapClaimsEnricher` adds claims at sign-in and on every refresh, and is how a tenant reaches `IUserInfo.TenantId` |
| Session | The cookie carries CAP's tokens. `CapCookieEvents` refreshes them inside cookie authentication a minute before the access token expires, reading CAP's live state, so a role granted in CAP appears within fifteen minutes and an account withdrawn there is signed out at its next refresh. An unreachable CAP is tolerated for a grace period |
| Account rules | The shared rules are pointed at local endpoints that refresh first and then hand over to CAP's page, so a user just back from enrolling an authenticator is let through rather than sent round again. A role refusal is a plain 403 for the application to style |
| Roles | An application extends `SystemRoles`, which declares none of its own, and publishes the catalogue to CAP. `SyncCapRolesAsync<AppRoles>` publishes once at startup and fails the application if CAP refuses; `CapRoleSyncJob<AppRoles>` is the same work as a JC.Core `IBackgroundJob` for JC.BackgroundJobs. CAP marks what a publish no longer names stale, never deleted |
| API | `CapApiClient` calls CAP as the application with a client-credentials token it obtains and renews itself: application info, members, one member by id, and the catalogue publish. A refusal is a `CapApiException` carrying CAP's reason |
| Cache | `CapUserCache` holds the live members in memory for a configurable window, one entry per member, refreshed together under a lock, with a miss on a fresh set answered without a call to CAP |
| Links | `CapLinks` builds the absolute, branded URLs into CAP's account pages from the host and client id already configured |

`AddCap` also configures the OpenIddict client: ephemeral keys with state tokens protected by Data Protection, token storage off so no OpenIddict tables are needed, and both callbacks passed through to JC.CAP's own endpoints. A `configureClient` hook hands the application the builder afterwards for certificates or a resilience pipeline.

JC.CAP depends on `CAP.SSO`, the contract package published from the CAP repository, and on `OpenIddict.Client.AspNetCore`, `OpenIddict.Client.SystemNetHttp`, `OpenIddict.Client.DataProtection` and `Flurl.Http`.

See the [JC.CAP documentation](../../JC.CAP/Setup.md).

## JC.Identity.Shared and JC.Identity.Shared.Web

**Return URLs on rule redirects.** `IdentityRuleSet` gains `ReturnUrlParameter`, defaulting to `ReturnUrl`. Both `IdentityRules.GetRedirect` overloads take an optional trailing `returnUrl`, and where one is given and the route is local the route comes back with it appended, URL-encoded, so the page can return the caller once the rule is satisfied. A route pointing at another host is returned unchanged. `IdentityMiddleware` passes the request's path base, path and query string, the same value the cookie handler's own challenge builds. Existing callers compile unchanged.

**`RoleRecord`.** A positional record of `Role` and `Description`, in `JC.Identity.Shared.Models`, now what a roles class reflects to. The reflection itself moved from JC.Identity into an internal helper on `IdentityHelper`, visible to JC.Identity and JC.CAP, so both authorities read a roles class the same way.

## JC.Identity

**`SystemRoles.GetAllRoles<T>()` returns `List<RoleRecord>`** rather than `List<(string Role, string Description)>`. Deconstruction and the `Role` and `Description` members work as before, so a `foreach (var (role, description) in ...)` or a `.Role` read compiles unchanged. A variable or parameter typed as the tuple list needs its type changed. Nothing else in the package changed.

## JC.Core

**`LocalUrlHelper`**, in `JC.Core.Helpers`. `IsLocal` applies the same test as `IUrlHelper.IsLocalUrl`, and `OrDefault` returns the URL where it is local and a fallback, `/` by default, otherwise. For a minimal endpoint or a service that has no `IUrlHelper` to ask before redirecting to a return URL.

## Also in this release

**Redundant package references removed.** `Microsoft.Extensions.Configuration.Abstractions` from JC.Github, JC.MySql, JC.SqlServer and JC.SqlServer.Hangfire, `Microsoft.Data.SqlClient` from JC.SqlServer.Hangfire, and `Microsoft.EntityFrameworkCore` from JC.Tenancy. Each arrives transitively through JC.Core or the provider package, so nothing a consuming application restores has changed.

**`CoreHelpers.PackageVersion`** reads `7.1.0`.

## Upgrading

Update the package versions and rebuild. There are no schema changes and no migrations.

One compile-time change is possible: code that holds the result of `SystemRoles.GetAllRoles<T>()` in a variable typed as `List<(string Role, string Description)>` needs the type changed to `List<RoleRecord>`. Code that deconstructs the result or reads `.Role` and `.Description` is unaffected.

An application taking JC.CAP needs the `CAP.SSO` package available on the same feed, and an application registered at CAP by a CAP operator.
