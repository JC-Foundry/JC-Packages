# JC-Packages v6.1.0

**Release date:** 19 August 2026
**Previous version:** 6.0.1

## Overview

A minor release, additive throughout. It brings one new package — **JC.Content** — and one substantial feature to JC.FileStorage: **read-only static files**, put in place at deploy time rather than uploaded.

Nothing is removed and no schema changes. Seven public members are now marked `[Obsolete]` as warnings, none of them errors, and every one still behaves exactly as it did. They are listed in full below, and that is the only part of this release that asks anything of an existing application.

Per the [suite versioning policy](../../../README.md#versioning-strategy), every package moves to `6.1.0`, including those with no functional change.

## Highlights

- **New: JC.Content** — profanity moderation with evasion-aware matching and confidence scoring, content diffing, conversion between plain text, Markdown and HTML, HTML sanitisation, and Unicode normalisation. No database, no ASP.NET Core dependency and no configuration.
- **New: static files in JC.FileStorage** — read-only documents served from a deploy-time directory, with automatic discovery, an in-memory cache and no database record.
- **`ContentSanitiser` has moved to JC.Content.** The JC.Web original is obsolete and forwards to nothing — it is the same implementation, kept in place and marked as a warning.
- **File validation and normalisation extracted into helpers** in JC.FileStorage, so the managed and static file types share one implementation. The old statics on `FolderModel` and `SavedFile` are obsolete.
- **`CoreHelpers` is now public** in JC.Core, carrying the suite's package name and version constants.
- EF Core and the `Microsoft.Extensions` packages move from `9.0.17` to `9.0.19`.

## New: JC.Content

A package for working with content itself, with no interest in where it came from or where it is going. It reads no configuration, touches no database and has no ASP.NET Core dependency, so it behaves identically in a request, a background job and a console application.

```csharp
builder.Services.AddContentManager();
```

Five feature areas:

| Area | What it does |
|------|--------------|
| Moderation | Finds profanity through the evasions people actually use — case, accents, repeated letters, punctuation between the letters, leetspeak, masking characters, Cyrillic and Greek look-alikes, and Latin letters standing in for one another. Every fold is recorded, and only those that could fabricate a match from innocent text are priced, so a finding carries a confidence percentage rather than a yes or no. Reporting, masking, removal and tagging are separate operations |
| Comparison | Diffs by line, word or character. The splitting is lossless in both directions, so the segments reconstruct either version exactly and each carries its index into both |
| Conversion | Moves between plain text, Markdown and HTML, with HTML as the hub. Structural rather than cosmetic: markup the target cannot express is dropped and its content kept |
| Sanitisation | Allowlist-based sanitisation for editor output, with `RichText`, `Basic` and `Empty` presets and `data:` URIs narrowed to images |
| Normalisation | A safe Unicode pass — lone surrogates, invisible characters, composition, line endings — kept separate from the folds that change what was written |

`ContentManager` runs them as a pipeline. Where a conversion involves HTML, it orders moderation against conversion so that HTML is never the text being scanned, since masking inside a tag, attribute or URL would corrupt the markup.

Terms come from a curated set and a bundled third-party list (MIT, [dsojevic/profanity-list](https://github.com/dsojevic/profanity-list)), embedded in the assembly rather than copied to output. An application can add its own terms, remove ones it disagrees with, or allow words producing false positives — at registration or at runtime.

See the [JC.Content documentation](../../JC.Content/Setup.md).

## New: static files in JC.FileStorage

Managed files are uploaded, recorded in the database and owned by a tenant. Static files are none of those things: they are read-only documents placed beneath a configured directory at deploy time by a developer or a build step, and served without a database record of any kind.

```csharp
builder.Services.AddFileStorage(useStaticFiles: true);
```

```json
{
  "FileStorage": {
    "StaticPath": "wwwroot/static-content"
  }
}
```

Files under that path are discovered automatically at first use, or registered explicitly:

```csharp
app.Services.AddStaticFiles(throwOnFail: true,
    new StaticFile("terms.pdf"),
    new StaticFile("privacy.pdf", "legal"));
```

`StaticFileService` reads them, `StaticFileCache` holds them in `IMemoryCache` for a configurable period (ten minutes by default), and `StaticFileRegistry` is what resolves a name and optional subfolders to a file.

Two behavioural notes worth knowing:

- **The blocked-extension list does not apply to static files.** It exists because an uploaded file is untrusted; a static file was put there by whoever deployed the application. What the application is willing to serve is its own decision.
- **Discovery runs on first resolve, not at startup.** The registry is a singleton built by a factory, so a missing `FileStorage:StaticPath` surfaces as an `InvalidOperationException` the first time something asks for a static file.

No `DbSet`, no table and no migration.

## Obsolete members

Every one of these is marked `[Obsolete]` with `error: false`, so existing code still compiles with a warning, and every one forwards to its replacement and behaves identically. Nothing here needs to be changed today.

### JC.Web — `ContentSanitiser` has moved to JC.Content

| Obsolete                                    | Replacement                                         |
|---------------------------------------------|-----------------------------------------------------|
| `JC.Web.UI.Helpers.ContentSanitiser`        | `JC.Content.Helpers.ContentSanitiser`               |
| `JC.Web.UI.Helpers.ContentSanitiserOptions` | `JC.Content.Models.Options.ContentSanitiserOptions` |

The implementation is unchanged — the same allowlists, the same presets, the same narrowing of `data:` URIs to images. It moved because sanitising HTML is content work rather than web work, and JC.Content can be used from a console or worker host where JC.Web cannot.

Both packages still reference `HtmlSanitizer`, so an application taking both is not paying for it twice in behaviour, only in a duplicate type name. Update the `using` and the type resolves.

### JC.FileStorage — validation and normalisation moved to helpers

`ValidationHelper` and `NormalisationHelper` (both in `JC.FileStorage.Helpers`) now hold this logic, so the managed and static file types share one implementation rather than each carrying its own.

| Obsolete                                       | Replacement                                            |
|------------------------------------------------|--------------------------------------------------------|
| `FolderModel.MaxAllowedBytes`                  | `ValidationHelper.MaxAllowedBytes`                     |
| `FolderModel.BlockedExtensions`                | `ValidationHelper.BlockedExtensions`                   |
| `FolderModel.IsBlockedExtension(string)`       | `ValidationHelper.IsBlockedExtension(string)`          |
| `FolderModel.NormaliseExtension(string, bool)` | `NormalisationHelper.NormaliseExtension(string, bool)` |
| `SavedFile.NormaliseFileName(string)`          | `NormalisationHelper.NormaliseFileName(string)`        |

`NormalisationHelper.GetFileName(string, string)` is new alongside them and has no obsolete counterpart.

> **Note:** JC.Content also has a `NormalisationHelper`, in `JC.Content.Helpers`. An application referencing both packages with both namespaces in scope will need to qualify the type. They are unrelated — the JC.FileStorage one normalises file names and extensions, the JC.Content one normalises text.

## Also in this release

**JC.Core — `InternalHelpers` is now `CoreHelpers`, and public.** The shared `ToDisplayName` implementation behind the string and enum extensions was internal; it is now a public static class carrying the suite's own identifiers:

```csharp
CoreHelpers.PackageVersion;              // "6.1.0"
CoreHelpers.PackageDisplay();            // "Using JCP v6.1.0"
CoreHelpers.PackageDisplay("Powered by", displayNameOverride: "JC-Packages");
```

Nothing was removed — the old type was internal, so no consuming code could reference it.

**JC.FileStorage — response records gained a shared base.** `GetFileResponseBase` now derives from a new `ResponseBase`, which `GetStaticFileResponse` shares. `Result` and `ErrorMessage` moved onto it and are now get-only rather than `init`, and the base constructors are `protected` rather than `public`. These types are constructed by the library; code that only reads them is unaffected.

**JC.FileStorage.Web** — `FormFileHelper` now calls the extracted helpers rather than `FolderModel`, so it no longer raises the obsolete warning itself.

**JC.Tenancy** — a pattern-matching tidy-up in the duplicate-registration guard. No behavioural change.

**Dependencies** — `Microsoft.EntityFrameworkCore`, `Microsoft.EntityFrameworkCore.Relational`, `Microsoft.Extensions.Configuration.Abstractions` and `Microsoft.Extensions.Hosting.Abstractions` move from `9.0.17` to `9.0.19`.

## Upgrading

Update the package versions and rebuild. There are no breaking changes, no schema changes and no migrations.

Two warnings may appear, both new and both harmless:

- `JC.Web.UI.Helpers.ContentSanitiser` — take JC.Content and change the `using`, or leave it and stay on the JC.Web copy.
- The `FolderModel` and `SavedFile` statics — point them at `ValidationHelper` or `NormalisationHelper`.

Neither is scheduled for removal in this major version.
